# SchulHub security

Who we defend against:

1. **Curious, clever students** with an account: they open the console, edit and replay
   requests, guess ids, and upload hostile files to see what happens.
2. **Hostile or buggy apps**: uploaded code runs in other people's browsers.
3. **Outsiders** who find the site and have no account.

The users are minors, so the default everywhere is: deny, collect less, show less.

`npm test` runs the attack tests in `test/security.test.js`. Each section below names the
tests that try to break it. Things checked by hand in a real browser are marked *(browser)*.

## Threats and how each is handled

### Sign-in and sessions

| Threat | Handling |
|---|---|
| Accounts outside the school | Tenant-specific Microsoft authority, plus a check of the `tid` claim. E-mail domain must be in `STUDENT_EMAIL_DOMAINS` / `STAFF_EMAIL_DOMAINS`; anything else is refused. |
| Passwords leaking | The Hub has none. No self-registration. Microsoft tokens are discarded after sign-in; only `openid profile email` is requested. |
| Session fixation / theft | New session id at login. Cookie is `HttpOnly`, `SameSite=Lax`, `Secure` under HTTPS, and named `__Host-…` under HTTPS so no subdomain can set or shadow it. Absolute lifetime 8 hours. Logout destroys the session server-side. The database stores only a hash of the session id. |
| Login CSRF / code injection | `state` and PKCE verifier live in the server-side session and are single-use. |
| Locking everybody out of sign-in | A whole school shares one address, so no limit on the way in can refuse a sign-in because of what somebody else at that address did. Starting a sign-in is limited per browser session (every Hub page has already given the browser one). A start from a browser without a session (a direct link on a first visit, or a script) counts per address; over that limit it is sent to the start page, which gives it a session, instead of being refused. A callback is only looked at when that browser really started a sign-in; any other callback is refused without counting and without asking Microsoft. Failed sign-ins never block anyone; their per-address count only keeps a flood of them out of the audit log. |
| An SDK token outliving its session | The session store caps a signed-in session's stored expiry at sign-in + 8 hours, however often the session is saved (`src/sessions.js`). The SDK API, which only looks at the stored session, therefore refuses the session's tokens from then on, even without another Hub request. Test: *Sitzungsspeicher: eine Anmeldung wird nie über die feste Höchstdauer hinaus gespeichert…* (`test/regressions.test.js`) |
| Open redirect after login | Return target must be a local path. |
| Test login reaching production | `/dev/login` only exists with `--dev`; `--dev` refuses to start unless `BASE_URL` is localhost and `NODE_ENV` is not `production`, and listens on loopback only. Real mode refuses to start with incomplete configuration. |

### Permissions

| Threat | Handling |
|---|---|
| Missing check on some route | Default deny: a global gate rejects every request without a valid session except a short allow-list. Every route then loads its object through a helper that checks this user against this exact class / app / version / student. |
| Browser-supplied role or owner | Never read. The user row is loaded from the database on every request, so role changes and blocks apply immediately. All decisions are in `src/access.js`. |
| Guessing ids | Ids are 96-bit random. "Not found" and "not allowed" return the same 404. |
| Teacher reading outside their classes | A teacher sees a student's app data only if the student is in one of **their** classes and the app is approved in **that** class. |
| App owner reading users' data | Owning an app gives no access to other people's saves or results. |
| Reviewer seeing private drafts | A teacher sees only the versions submitted to or approved in their classes. |
| Student swapping code after approval | Approval is bound to a version. A newly published version waits; the class keeps the approved one. Versions are immutable once uploaded. |
| CSRF | Every non-GET request needs the per-session token (form field or header) and, if present, a matching `Origin`. `SameSite=Lax` on top. |
| Join codes | 192-bit random, expiring (15 minutes to 1 week), one active code per class, revocable. A code can only ever insert a `student` membership. Wrong attempts are rate-limited per account. |

### App isolation

| Threat | Handling |
|---|---|
| App reads Hub cookies, pages or DOM | Each app has its own origin (`<random key>.<apps domain>`) on a registrable domain of its own – the Hub refuses to start when the apps domain shares a parent domain with the Hub (see below). No Hub cookie is ever sent there. The app runs in an `<iframe sandbox>` without top-navigation or popups; the same sandbox is repeated as a CSP header on the app's documents. *(browser: cookie empty, `parent.document` and `top.location` blocked)* |
| App reads another app's data | Every data query is keyed by the app resolved from the request's host. The SDK token names one app and is rejected on any other app's origin. |
| Stolen or replayed token | SDK tokens are HMAC-signed, expire after 10 minutes, and are bound to user, app and session: after logout or a block they stop working at once. File tokens are a different kind and cannot be used as SDK tokens. |
| A call still arriving while things change (the account is deleted or blocked, the person is removed from the class, the class is archived, the app is deleted) | The SDK API checks the token when a call arrives – before its body is read, so strangers' bodies are never buffered – and again once the body is there (`appsHost.js`, `callerNow`; the same for `hub.files` uploads). What the call does is decided by the state at that moment: a deleted or blocked person gets 401, a deleted app 404 – never a 500, and nothing is stored for a person who no longer exists (no row, no `hub.files` content on disk). A result whose body arrives after a removal from the class or after archiving is filed without the class; class data of an archived class cannot be written. Uploads to the Hub (folder file, editor save, ZIP) check after reading the body that their version, draft or app still exists (404 otherwise, nothing written to disk). A ZIP whose account is deleted while it is unpacked leaves no audit entry naming the person or the app (`upload_abgelehnt` is written only while both still exist). Tests: *Konto löschen, während der Inhalt eines Aufrufs noch unterwegs ist…*, *Konto löschen, während eine App hochgeladen wird…*, *Aus der Klasse entfernt, während gespeichert wird…*, *Klasse archivieren während gespielt wird…* (`test/races.test.js`) |
| App sends data out | App CSP allows network access only to the app's own origin. The Hub's `frame-src` blocks the app from navigating its frame elsewhere. *(browser: `fetch` to the internet and to the Hub blocked, self-navigation blocked, popup blocked)* |
| Forged messages between app and Hub | The Hub page accepts messages only from the app's origin **and** its own frame, and replies only to that origin. The SDK accepts messages only from the Hub origin and its parent window. |
| App opened outside the Hub | Top-level requests (`Sec-Fetch-Dest: document`) are refused; `frame-ancestors` allows only the Hub. |
| Unpublished code visible to others | Files are served only with a signed token for exactly that version, issued after a permission check. |
| Apps learning identities | Apps get a display name and a per-app pseudonymous id. No e-mail address. |
| A preview writing real data | A preview (an owner trying a version, a teacher reviewing a submission) gets an SDK token marked as preview. The mark is inside the signed token, so the app cannot remove it. The SDK API then keeps every write in memory (`src/sdkStore.js`): bounded per preview (2 MB), in number (400) and overall (128 MB), dropped after 2 hours idle or on restart. Reads of class and app data fall through to the real data, writes never do. Previews are not counted as plays, and a preview leaderboard shows no real players. |
| An app setting cookies for the Hub, or a cookie bomb that locks a browser out of the Hub | Cookies are scoped to a whole registrable domain. In real mode the Hub refuses to start when its host and `APPS_DOMAIN` share a parent domain of two or more labels (`hub.meine-schule.de` + `apps.meine-schule.de` share `meine-schule.de`); the message names a separate domain to use instead (`src/config.js`, `addressProblems`). The only override is `APPS_PUBLIC_SUFFIX` set to exactly that shared suffix, for an operator who confirms it is a public suffix (like `co.uk`). Real mode also refuses a `BASE_URL` without `https://` (only `localhost` and `127.0.0.1` may use `http://`), so the session cookie is always `__Host-` and `Secure`, and `APPS_DOMAIN` must be a plain host name (no scheme, `*`, port or path). `APPS_PUBLIC_SUFFIX` is the operator's statement that the shared part is a public suffix: set to the school's own domain, it switches this protection off. |
| The next person on a shared PC finding what an app stored for the previous one (localStorage, IndexedDB – where Godot and Unity save –, caches, service workers, cookies) | Before an app's own code runs, its frame shows a page of the Hub on the app's origin: `GET /~<file token>/_hub/start` (uploads can never create `_hub/` paths, any letter case). It needs a valid file token for exactly that app and carries a marker for the person the token was issued to: an HMAC of app id and user id with the session secret (`tokens.pseudonym('storage', …)`) – never a name, e-mail or id, the same in every session, different in every app. Its script is a Hub file (`/_hub/start.js` = `sdk/hub-start.js`, external, cacheable by content hash); the page has its own CSP (`default-src 'none'; script-src 'self'`, `frame-ancestors` the Hub, sandbox), `nosniff`, `no-store`. If the marker kept in the origin's `localStorage` differs (or is missing), the script deletes localStorage, sessionStorage, every IndexedDB database (`indexedDB.databases()`), Cache Storage, service worker registrations, the origin private file system and every cookie scripts can see (with `Domain=` of every parent label), then keeps the new marker. The same person again: nothing is touched, so a pupil's own device keeps its saves. Then it tells the Hub page by `postMessage` – to the Hub origin only – and the Hub page loads the app (`public/player.js`; only an address on that app's origin, with `location.replace`). The player holds its frame in a `<template>` until then. Pages that frame an app with a plain file token (review workbench, editor preview, any later page) are sent through the start page by the app origin itself: a frame navigation (`Sec-Fetch-Dest: iframe`) with a token not marked `r: 1` gets a 303 to it; only the player and the start page (a copy of the token with `r: 1`) issue marked tokens. A cleanup that cannot finish (a database still open in another tab, an API that does not answer within 3 s) lets the app start but keeps no marker, so the next start clears again. Cost, measured in Chromium (loopback, median of 15, page start → app loaded): player 16 → 24 ms, review 18 → 26 ms, editor 16 → 29 ms; after another person's leftovers +9 ms (the cleanup itself takes about 2 ms). *(browser: the review's repro – Sina's diary in localStorage – is gone for Pia; all six example apps load and save in the player, the review preview and the editor preview, also after "reload", without console errors)* |
| A student changing what classmates see after approval, without a new review (app-wide shared data) | `hub.shared` reaches everyone who opens the app and nobody reviews it. Writing it (`shared.set`, `shared.remove`) is allowed only in apps whose owner is staff (teacher or admin) – by the owner or the admin, as before. In an app of a student every write is refused for everybody (owner, classmates, teachers, admin), in previews too, with the code `read_only` and a German message; reads are unchanged. Class data (`hub.classData`) stays with the class's teachers in any app. |

### SDK features of version 2

| Threat | Handling |
|---|---|
| App unlocks arbitrary "achievements" (e.g. offensive titles shown in the Hub) | Only achievements declared in the version's `schulhub.json` can be unlocked. The manifest is uploaded data: parsed as JSON (never executed), validated field by field (`src/manifest.js`), lengths capped, emojis from a fixed list. It is part of the version the teacher reviews. Titles are always shown escaped. |
| App changes per-class settings | There is no write path from apps (`settings.set` does not exist). Teachers edit settings in the Hub; values are validated against the manifest's field types and capped at 64 KB. Apps read only the settings of the class they were opened from. |
| Files as an attack channel (`hub.files`) | Per person and app only. Allow-list of passive types (PNG, JPEG, WebP, GIF, JSON, text, CSV); images must start with the right magic bytes, JSON must parse; no HTML, no SVG. Stored by content hash in `data/userfiles/` (apart from app code), names validated like keys. Served on the app's origin only, with the stored type, `nosniff`, `Content-Disposition: attachment` and the app CSP. 1 MB per file, 50 files and 10 MB per person and app, rate-limited. Deleted with the person's app data or account (contents garbage-collected). |
| Progress values | Numbers only, clamped to 0..1; label capped at 60 characters. |
| Previews | All of the above go to the in-memory preview store during a preview, like saves and scores. |
| Uploaded copies of Hub files | `hub-sdk.js` and `hub-ui.css` (at any path) and fonts under `hub-ui-fonts/` are always served from the Hub's own files. |

### Editor drafts: data model

| Threat | Handling |
|---|---|
| Changing code after approval through the editor | The editor writes to one mutable **draft** per app (`app_drafts`, `draft_files`), never to a version. "Save as version" copies the draft's rows into a new version, which is immutable like any upload and goes through the same publish and review rules. |
| Draft files bypassing upload rules | Every draft write goes through the same path, extension, size, file-count, version-size and account-quota checks as uploads (`uploads.putDraftFile`). Drafts count toward the account quota. |
| Others reading a draft | Draft files are served only with a file token that names the draft (`d: 1`) for exactly that app, issued after `canManageApp`; never cached (`no-store`). A version token never reads draft files and vice versa. Draft previews always use the in-memory SDK store. |
| Deleting a draft deleting a version's files | Content blobs are shared; garbage collection keeps a blob while any version or draft references it. |

### Editor drafts: the editor and its file API

| Threat | Handling |
|---|---|
| Someone else reads or edits a draft | Every `/studio/:appId…` route loads the app and checks `access.canManageApp` (owner or admin) before anything else; everybody else – also a teacher who reviews the app and the app's players – gets 404. For `PUT` the check runs before the request body is read. |
| Forged requests | `PUT` and `POST` need the session's CSRF token (header `X-CSRF-Token` from the editor's script, form field for the version form) and a matching `Origin`, as everywhere in the Hub. |
| Path tricks, hidden or reserved names, wrong types, big files, full accounts | Every write goes through `uploads.putDraftFile` – the same name, type, size, file-count, version-size and account-quota checks as an upload. Reading looks a name up in the draft's rows only (exact match), never on disk. Renaming writes the content under the new name through `putDraftFile` and removes the old row in one transaction; it never overwrites another file (409). The moved file frees its place and bytes in that check (`moving`), so a rename works at the file, version-size and account limits instead of failing as "zu viele Dateien". `?neu=1` (new files, uploads) never replaces. The file API never creates a draft by itself (409 without one). |
| Flooding | Rate limit `draftWrites` (600 per minute and person) on every write, after the permission check and before the body is read; a body is capped at `maxFileBytes`. "Als Version speichern" also counts against `uploadVersions`. |
| Uploaded code on the Hub's origin | The editor page never contains file content. Text files are fetched as JSON (`Cache-Control: no-store`) and live only inside CodeMirror's document (text nodes). Binary files are never sent to the editor (415) and images are not previewed on the Hub origin – the info panel shows name, size and how to use the file, as text. File names are escaped (`html```) or set with `textContent`. |
| The draft leaking through the app origin | The preview is the player's stage with a draft file token (`d: 1`, one hour) that only the owner's editor page or `GET /studio/:id/vorschau` (owner only) issues. A version token never reads draft files. The SDK token of a draft preview is always a preview (`p: 1`): nothing is stored, nothing counts as a play. |
| Changing approved code through the editor | Unchanged rule: the editor only writes the draft. "Als Version speichern" (`services.versionFromDraft`) makes a new, immutable version that needs `index.html` and goes through publish and class review like an upload. |
| Losing work by accident | Starting a draft from a version never replaces an existing draft unless `ersetzen=1` is sent; a template never overwrites a draft; discarding is a POST behind a confirmation that says what happens. The editor warns before leaving with unsaved changes and saves before its own links leave the page. |

### Templates, ZIP downloads, playground

| Threat | Handling |
|---|---|
| Templates as a way around upload rules | Templates are fixed files in the repository, checked when the Hub starts (allowed names and types, `index.html`, valid `schulhub.json`, no copies of `hub-sdk.js` / `hub-ui.css`); the Hub refuses to start with a broken template. The id in a URL is only looked up in that list, never used as a path. A new app from a template puts every file through `putDraftFile` inside one transaction: if anything is refused (for example a full account), no app, no draft and no orphaned file content remain. |
| ZIP downloads | Fixed file names, `Content-Disposition: attachment`. Content chosen by the server only: the template's files, `hub-sdk.js`, `hub-ui.css` and the four UI fonts – nothing from the database. |
| The playground | `POST` only. It creates the person's own app once (an ordinary app under all the usual rules) and reuses it afterwards; nobody else's app is ever opened. |

### Classes: review, co-teachers, archive

| Threat | Handling |
|---|---|
| Approving something other than what was reviewed | Every change to an app in a class goes through one state machine (`src/classApps.js`). Approving and giving back name the exact waiting version; anything else is refused. |
| A returned app vanishing from the reviewer | A returned version stays visible to the class's teachers (`request_state = 'returned'`) and the reason is kept as a review comment. The owner can resubmit; the student gets an in-Hub notice. |
| Removing an app destroying results | An app that was ever approved becomes `removed`: not playable any more, but its results stay readable for the class's teachers. Publishing a new version never brings it back. "Ever approved" is the class row's kept `version_id` (`access.wasApprovedIn`, used by `canSeeClassResults` and `canSeeStudentData`): when the owner submits a removed app again, its results stay readable while the submission waits and after it is given back, the Apps tab keeps it under "Entfernte Apps" with its results ("Zurückholen" only for `removed`), and feedback can still name it. |
| Students bypassing review by "sharing" | Sharing with colleagues (`apps.shared`) only works for apps whose owner is staff (`access.isSharedWith`). A colleague may preview the shared app's published version before adding it: the catalogue and search link (`/apps/:id/spielen`) opens it as a preview (`access.resolvePlay`, nothing is stored, the back link goes to the catalogue). Students never get it. |
| Co-teacher invitations used by students | A join code has a role. A class code always creates a **student** membership, whoever uses it. A teacher invitation creates a teacher membership only for staff accounts; a student using it gets nothing. One active code per class and role. |
| Archived classes | Read-only (`canChangeClass` is false). Students lose access and class context; nobody can join; teachers keep read access to results. The SDK gives **no class context** in an archived class, even with a token issued before archiving – so no class data can be written and no results are filed into it. Archived classes do not count for "shares a class" on leaderboards. Tests: *Archivierte Klassen…* |

### Class pages and teaching tools

| Threat | Handling |
|---|---|
| Student or foreign teacher creates, edits or deletes assignments | `access.canAssign` (teacher of an active class + app approved there), `canManageAssignment` for edit/delete. Everything else answers 404. |
| Ticking an assignment "done" for someone else | `POST /aufgaben/:id/erledigt` only writes a row for the signed-in user (`access.canMarkDone`: student of the class, class active). Any user id in the form is ignored. "Done" is otherwise derived from results / full progress after the start (`src/assignments.js`). |
| Students seeing other classes' assignments, or planned ones before their start | `access.canSeeAssignment`: may view the class, and for students only from `starts_at`. Before that the page, "erledigt" and "offen" answer 404, no notice is sent at creation (a planned assignment moved to "now" notifies then; one moved into the future again loses its notice), and feedback cannot be linked to it. Archived classes are invisible to students. Test: *Geplante Aufgaben: vor dem Start sehen Schüler/innen nichts davon…* (`test/people.test.js`) |
| Teacher reading a class that is not theirs | Every class page, tab, result list, CSV, student detail, overview and settings page loads the class and checks `canManageClass` / `canChangeClass` / `canSeeClassResults` / `canSeeStudentData`; not allowed = 404. |
| Results without a class | A result recorded without class context (e.g. a school-wide app at home) has `class_id` NULL and never appears in any class view. Results from before version 2 are marked `''` ("class unknown") by migration 3 and remain visible to the teachers of the app's classes, as before. Assignment state counts only results of the assignment's own class (progress, being personal, counts everywhere). Test: *Aufgaben zählen nur Ergebnisse aus ihrer Klasse…* |
| Results leaking between classes | Teacher views (results list, student detail, CSV, overview grid, weekly charts, assignment detail) only count results with `class_id = <this class> OR class_id = ''` (`''` = recorded before version 2, class unknown). Results recorded without any class (`class_id IS NULL`, e.g. at home in a school-wide app) appear in no class view. Tested with one student in two classes and a result made at home. |
| Removed app hides earlier results from its teacher | `canSeeClassResults` allows status `approved` or `removed`; removed apps keep "Ergebnisse" and can be brought back (`classApps.restore`). |
| Private feedback read or written by the wrong person | Writing: `canGiveFeedback` (teacher of an active class → a student of that class). Optional links to an app / assignment are checked against the same class. Reading: `canReadFeedback` (the student, the class's teachers). Marking read: only the student (`canMarkFeedbackRead`), by POST – looking never changes state. Deleting: `canDeleteFeedback` (author, the student, admin). Length ≤ `limits.feedbackChars`. The notification text is composed by the server. |
| Co-teacher invitation misused | Created only by teachers of the active class (`canChangeClass`) with `services.createJoinCode(…, 'teacher')`; usable only by staff accounts (`access.joinRoleFor`); never shown to students; revocable; audited (`lehrkraft_eingeladen`, `einladung_geloescht`). A class code still always makes a student. |
| A class left without a teacher | `access.canLeaveClass`: a teacher may leave only while another teacher remains; otherwise the page points to archive / delete. |
| Changes to an archived class | Every change goes through `canChangeClass` (not archived), including the app owner's "remove from class" path: `access.canRemoveFromClass` allows the class's teachers (and the admin), or the app's owner who can see the class – never while archived. Students lose access to the class, its assignments and its apps; restoring brings everything back. Archive / restore are audited (`klasse_archiviert`, `klasse_wiederhergestellt`). |
| Tampered per-class app settings | Only `canEditAppSettings` (teacher of the active class, app approved there). Fields come from the manifest of the version approved in the class; values are validated with `validateSettings` (unknown keys ignored, per-field errors), stored as JSON with `updated_by/at`, audited. ### Uploads

| Threat | Handling |
|---|---|
| Code running on the server | Nothing uploaded is ever executed, imported or interpreted. Files are stored as bytes and sent back as bytes. |
| Path traversal | File contents are stored under their SHA-256 hash; names exist only as database rows. No disk path is ever built from an uploaded name. Names are still validated (no `..`, absolute paths, backslashes, control characters, reserved `_hub/`). |
| Archive bombs | Limits on archive size, entry count, per-file and total unpacked size. Sizes are counted while unpacking, not trusted from the header. |
| Symlinks, encrypted or special entries | Rejected. |
| Dangerous file types | Allow-list of extensions; each is served with a fixed content type and `nosniff`. |
| Partial hostile upload left behind | A refused upload is deleted completely. |
| Uploaded content on the Hub origin | Never. The source viewer shows text escaped inside `<pre>`; downloads are `attachment` with a fixed file name. |
| Storage exhaustion | Quotas per file, version, app and account, checked against the declared size before a body is read (see *Large upload bodies* above); rate limits on uploads. |
| File names that look like other names (e.g. `bild⟨U+202E⟩gnp.js` shown as "bildsj.png") | Every stored name is refused if it contains a Unicode format character (`\p{Cf}`: bidi controls, direction marks, zero-width joiners, soft hyphen, BOM) or U+2028/U+2029 – folder upload, ZIP, editor new file, upload and rename. Messages show the character as `⟨U+202E⟩`. Names stored before this rule are shown with placeholders, are reported as an error when such a draft becomes a version, and can still be renamed or deleted. Test: *Dateinamen mit unsichtbaren Zeichen werden überall abgelehnt…* (`test/limits.test.js`) |

Tests: *Upload: Pfad-Tricks…*, *Upload: bösartige ZIP-Archive…*, *Speicherplatz pro Konto (maxUserBytes) gilt für Uploads…* (`test/regressions.test.js`)

### Injection

| Threat | Handling |
|---|---|
| XSS through names, comments, saved data, source code | All HTML is produced by a template function that escapes every value by default. The Hub's CSP is `default-src 'none'; script-src 'self'; style-src 'self'` – no inline scripts or styles exist. Icons and colours are chosen from fixed lists. |
| Typed text that looks different from what it is (bidi controls in names, notes, comments) | `cleanText` removes bidi embeddings, overrides and isolates (U+202A–U+202E, U+2066–U+2069) from everything people type; direction marks stay for right-to-left text; U+2028/U+2029 become plain breaks. Test: *Eingaben: unsichtbare Richtungszeichen verschwinden aus Namen und Texten…* (`test/limits.test.js`) |
| SQL injection | Prepared statements with bound parameters only. |
| Spreadsheet formula injection | CSV cells starting with `= + - @` are prefixed. |
| Host header tricks | Requests for unknown hosts are refused. |

### Abuse and operations

- **Rate limits** on sign-in, wrong join codes, state-changing requests, uploads, app files, SDK calls, editor writes, `hub.files` uploads and class submissions. A whole school usually shares one public address, so nothing that real use goes through can be blocked per address:
  - Sign-in is limited per browser session (see *Locking everybody out of sign-in* above).
  - Wrong join codes are limited per person. Codes are 192-bit, so a per-address limit would not slow down guessing; it would only let a group close joining for everybody.
  - App files count against the **person** the file token was issued to.
  - The only per-address counts are for invalid file tokens, for sign-in starts from a browser without a session (over the limit it is sent to the start page) and for failed sign-ins written to the audit log. None of them can refuse a valid request.
  - A person can submit a bounded number of apps to classes and publish a bounded number of versions per hour. Re-publishing a version that already waits adds no history, and the same unread notice is never repeated.

  Tests: *SDK-Aufrufe werden gebremst*, *Beitrittscodes…*, *Grenzen gelten pro Person…*, *Anmeldung: wer an der Schuladresse flutet…*, *Beitreten: falsche Codes anderer…*, *Gefälschte Datei-Links blockieren nur sich selbst…*, *Einreichen lässt sich nicht als Flut…*, *Veröffentlichen hin und her…*, *Allgemeine Schreibgrenze (rate.write)…*, *Upload-Start-Grenze (rate.uploadVersions)…* (`test/regressions.test.js`)
- **Quotas** per user and app for saves, shared data, results, leaderboards, comments, files (`hub.files`: per app and 50 MB per account across apps). Test: *Dateien aus Apps: Obergrenze pro Konto…*
- **Memory per person**: at most 4 upload bodies at a time across folder, editor, ZIP and `hub.files` uploads (`limits.parallelUploads`), 32 SDK API requests (`limits.parallelApiCalls`) and one data export (`limits.parallelExports`); sizes are checked before a body is read (see *Apps, uploads and review*). Tests: *Upload: höchstens 4 Dateien gleichzeitig pro Person…*, *Plätze pro Person gelten auf allen Wegen…*, *Meine Daten: ein zweiter Export derselben Person während des ersten wird abgelehnt (429)* (`test/limits.test.js`)
- **Personal pages are never cached**: every response to a signed-in person carries `Cache-Control: no-store` (shared school PCs, back button after logout). Test: *Persönliche Seiten…*
- **Audit log** of sign-ins, refused sign-ins, role changes, blocks, uploads, refused uploads, publishing, approvals, rejections, deletions and data exports. Readable by the admin only, pruned after `AUDIT_RETENTION_DAYS`.

- **Secrets** come from environment variables. `.env` and `data/` are git-ignored. Nothing secret is sent to the browser.
- **Dependencies**: six npm packages (`express`, `express-session`, `@azure/msal-node`, `yauzl`, `qrcode-generator`, `diff` – the last one server-side only, for review diffs), no build step. Nothing is loaded from another host; the maintainer scripts in `scripts/vendor/` rebuild the vendored files.

### Privacy (minors)

- Stored about a person: name, school e-mail, Microsoft object id, role, class memberships, last sign-in, and what apps saved for them. No IP addresses, no photos, no tracking.
- Teachers see names, never e-mail addresses. In apps approved in their class they also see the student's results from that class and what the app keeps for the student – saves, best scores, progress, achievements, also from home or another class – and when and how often the app was opened. The join page and `/datenschutz` say exactly this, from one text (`src/teacherView.js`); only the administration sees e-mail addresses. Test: *Was Lehrkräfte sehen: Beitrittsseite und Datenschutz sagen dasselbe wie die Lehrer-Seiten* (`test/people.test.js`)
- Leaderboards show a person's name only to people who are in at least one class together
  with that person, and never if the person chose to be anonymous. Everyone else – other
  classes, teachers of other classes, the whole school in a school-wide app – sees "Anonym".
  Test: *Bestenliste: Namen sehen nur Personen aus derselben Klasse…*
- "Meine Daten" shows everything, exports it as JSON, deletes per app or the whole account. Deleting an account removes its rows, anonymises the audit entries it made **and the entries about it** (`audit_log.subject_id`; older entries by exact name for account actions), deletes other people's in-Hub notices that name it (`notices.subject_id`) or point to its apps, and replaces the names of its apps in the audit log (app names are often personal). ## Where security won over a feature

- **No internet access for apps.** Costs authors the convenience of CDNs. Without it, any app could send student data to a third party.
- **Student app updates need re-approval.** Slower for student authors; otherwise approval would mean nothing.
- **Relative paths only, no top-level app pages.** Needed for per-version access tokens and the sandbox.
- **Class data is written by teachers, app-wide data only in teachers' apps.** A student's app cannot store anything all its users see (`hub.shared` is read-only there), even though a pupil's high-score message or level editor would be fun. Without it, the owner of an approved app could show the whole class anything, unreviewed.
- **Names of approved student apps are frozen** while a class sees them. Renaming means withdrawing and submitting again, so the teacher reviews the new name.
- **Another person's browser data is removed before an app starts.** On a shared PC the next pupil loses nothing of their own, but an app's offline cache (e.g. Unity's) is downloaded again after a change of person.
- **No public showcase.** Everything stays behind school sign-in; there is no public route that serves app files.
- **Multiplayer is prepared, not switched on** (see "Still open"): a live channel between minors needs moderation rules first.
- **No short typed join codes.** Joining stays QR code or link with 192-bit codes; a short code would be guessable and is a third way in.
- **Previews never write real data**, even though it would be convenient to keep what a teacher typed while reviewing.
- **Names on leaderboards only within shared classes**, even in school-wide apps.

## Still open

- **Microsoft sign-in was not exercised end to end in development.** The redirect to the tenant authority, the role mapping and the callback's own checks (state, code, Microsoft error, `tid`, `oid`, single use) are tested with a stand-in for Microsoft's library. The code exchange itself has not been run against a real tenant. Test it with a real school account before going live.
- **Leaderboard scores and results come from the app's code in the student's browser** and can be faked by the student. They are for fun and practice, not for grades.
- **A hostile app can act as the person using it, inside that app** (it holds their short-lived token by design). It cannot reach other apps or the Hub. Teacher review before approval is the control.
- **The SDK token is readable by the app** and contains internal random ids of user and class and the hash of the session id (`s`). These grant nothing on their own (the token is bound to the app's origin and the hash cannot be turned back into a session cookie) and are not personal data, but they are the same across apps.
- **Leaderboards as a covert channel.** An approved app could encode what it learns about its users into leaderboard scores (numbers only, at most 20 boards) that its author reads. Teacher review of the code is the control; scores never carry text.
- **Where permission decisions live.** Every decision about one object goes through `src/access.js`. List queries (search, catalogue, start page, queues) pre-filter in SQL with the same rules, and objects opened from them are checked again through `access.js`.
- **Rate limits and login state are in memory**, per process. Run one process, or move them to a shared store before scaling out.
- **Request floods are the reverse proxy's job.** The Hub does not throttle anonymous requests or sign-in attempts per address, on purpose: one person could then lock the whole school out. Every anonymous page view creates a small server-side session, kept 8 hours. Nothing a request sends can make it much bigger: a return address longer than 512 characters is not kept, and a form error only returns to the form (keeping what was typed) for signed-in people and short addresses. So a session without an account stays at about 1 KB (at most about 1.3 KB, when quotes and backslashes in the address are escaped on saving). Each sign-in that is really started makes the server ask Microsoft once. Put a request limit on the reverse proxy in front of the Hub. Test: *Ohne Anmeldung: eine lange Adresse…*
- **The review history can be pushed along.** One pupil can add about 60 "eingereicht" entries per hour to a class (publishing is limited to 60 versions an hour). Older entries stay stored but drop out of view (the app page shows 60, the workbench 80).
- **After an account deletion, a confirmation naming the person can still wait in the admin's own session** (for example "… ist jetzt Schüler/in."). It shows once on the admin's next page and is gone at the latest when that session expires (8 hours).
- **Apps share one apps domain.** Every app has its own origin, but all are subdomains of one registrable domain (`APPS_DOMAIN`). In one browser an app can set cookies for that whole domain and disturb the other apps – up to a cookie bomb after which every app answers 431 for months in that browser. The Hub itself is safe (it must be on another registrable domain, enforced at start). The start page deletes such cookies when a different person starts an app, but only if its own request still gets through. The complete fix is to put the apps domain on the Public Suffix List, so browsers treat every app as a site of its own. (Locally, `*.apps.localhost` is cross-site to the Hub, and apps cannot set cookies at all.)
- **Apps can tell that they run in a preview** (`hub.mode`, `user.isTeacher`), so a hostile submission can behave harmlessly while a teacher reviews it and differently after approval (review finding 9). Reviewing the code, not only the behaviour, is the control; the workbench shows the source and the changes.
- **Browser storage between two starts.** What an app stored stays in the browser until that app is started again; the start page removes it only then, and only for a different person. A tab left open after logout keeps its app running until it is closed (the app cannot reach the Hub any more – its token dies with the session – but could read what the next person's copy of that app stores meanwhile). A pupil with developer tools on the same PC can read leftovers before the start page runs. On shared PCs, use the browser's guest mode or let it clear browsing data on exit.
- **Previews in the review workbench and the editor rely on Fetch Metadata** (`Sec-Fetch-Dest`) to be sent through the start page. Browsers without it (Safari before 16.4) show those previews without the storage check. The player does not depend on it.
- **App-wide data written before this change** in apps of students stays readable to their users, and nobody can change or delete it through the SDK any more.
- **Lookalike code beyond bidi controls.** Invisible characters that JavaScript accepts inside identifiers – zero-width joiners, the Hangul filler U+3164 (`isAdmin` with a
  ZWJ is another variable) and lookalike letters from other alphabets (homoglyphs) are neither reported
  nor marked; ZWJ is part of emoji that children use in their code. Versions uploaded before the
  bidi check have no such findings in their stored report; the views mark the characters anyway.
- **One app can slow down its user's other apps.** The places for upload bodies (4) and SDK requests (32) belong to the person, not to one app: an app that keeps requests open makes the same person's other apps and Hub uploads wait (429) while it runs, until those requests end or time out (10 minutes). Other people are not affected, and closing the app frees the places.
- **Upload bodies are still buffered in memory**, at most 4 × 25 MB per person at a time. Many accounts
  at once can still add up; streaming file bodies to disk would remove this.
- **Teachers see saves, best scores, progress and achievements made outside their class** (at home, in another class) in apps approved in their class – by decision, and the texts for students say so. Results stay per class.
- **Text other people wrote about a deleted person** (feedback bodies, assignment titles they chose, announcements) is not rewritten when that account is deleted.
- **A planned assignment brings no notice at its start**; students see it on their start page from then on. And a student app renamed while its class was archived shows the new name when the class is restored, without another review. The same holds when the owner takes an app out of a class, renames it, and the teacher brings it back ("Zurückholen"): the teacher sees the new name, but it is not reviewed in the workbench.
- **Frame navigation blocking** was verified in Chromium only. Browsers that do not apply the parent's `frame-src` to later navigations would allow an app to navigate its own frame away (and leak what it knows about its own user).
- **App CSP allows inline scripts, `eval` and WASM** inside the app's own origin, because game engines need them. Containment is the origin and the sandbox, not the app's CSP.
- **No malware scanning** of uploads. Files are only ever delivered to browsers inside the sandbox; a teacher who downloads a zip should treat it like any download.
- **The admin can see everything**, and the database and blobs are not encrypted at rest. Protect the server, backups and the `data/` folder accordingly.
- **Godot/Unity builds that need threads** (cross-origin isolation) are not supported yet.
- **Multiplayer is prepared, not built.** The SDK has `hub.room()`, the API has `room.join`, the
  permission rule exists (`access.canJoinRoom`: active class, app approved there, teacher's
  opt-in `class_apps.multiplayer`), but there is no transport and every call answers
  `not_available`. Questions to settle before switching it on:
  - It is a channel between minors. What may travel (only structured game state, or any text)?
    Who can read it afterwards – nobody (ephemeral), or the teacher?
  - Moderation: can a teacher see who is in a room, mute or end it? What is logged (membership,
    never content)?
  - Abuse limits: message size and rate per person, room size, number of rooms per class.
  - Transport: WebSocket or Server-Sent Events on the app origin, authenticated by the same
    short-lived SDK token; it must die at logout and class removal like the token does today.
  - Preview: a preview must never join a real room.
  - Scaling: rooms live in memory in one process (same limit as rate limits today).
- **Backups contain all personal data and are not encrypted by the Hub.** Whoever holds the zip holds everything. Store it encrypted (e.g. an encrypted disk or `age`/`gpg`) and delete old backups according to the school's rules.
- **Browser backups are limited to ~3.5 GB and 65 000 files** (the zip writer has no ZIP64). Larger installations back up the `data/` folder on the server (stop the Hub, copy the folder).
- **`VACUUM INTO` and `PRAGMA quick_check` block the Hub briefly** on large databases (seconds); run them outside lessons.
- **Two tabs editing the same draft**: the last save wins (no locking).
- **No formal privacy review.** Before real use, the school's data protection officer should check this against the school's obligations.
